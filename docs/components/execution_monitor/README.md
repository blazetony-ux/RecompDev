# Live execution monitor

**Latest v0.4.9.23 contract:** v0.4.9.23: watched PC hits are counted exactly but instruction detail is sampled/coalesced after early examples. Periodic/final summaries, separate display decimation and explicit capture-truncation flags prevent a misleading full-trace claim; no execution control.


**Scope:** `developer-debugger`. **Version:** `0.1.0`. Canonical registry: `workspace/components.json`.

`python -m execution_monitor.viewer` is spawned separately by the host launcher only with `-ExecutionMonitor`. It subscribes to the **controller diagnostics service**, not to any CPU, VDP, video, ROM, device or raw trace. It displays sampled instruction transitions (guest PC and next PC, raw opcode byte and classification, SP, cycles, steps), input masks, frames and stop events. It is deliberately **not a validated Z80 disassembler**; no assembly mnemonic guarantee. Adapter `execution_monitor/bridge.py` stages a neutral `rd_execution_events.hpp` publisher in the copied generated `live_sms.hpp`, leaving `translated.cpp`, original generator and all frozen baselines untouched. Future CPU adapters provide the same event schema without monitor changes. Default one instruction sample per 256 reported guest steps (`-MonitorEvery` changes it, minimum 1; output bounded at 200,000 events). The monitor stays open showing the last events even when controller disconnects after guest stop. No pause, step, breakpoints or ROM-free execution in this version. If Tk is unavailable, the launch log records the error; it is not proof of a visible GUI.

## v0.4.9.19 current-controller preview path

The compiled controller now exposes `preview --job JOB_ID`. It launches a separate `job_preview.py` diagnostics worker rather than connecting the viewer directly to guest plugins. The worker verifies ROM source identity, job/orchestration source hash, native translation manifest and exact maintained interactive/CPU adapter templates before staging. Original `translated.cpp`, original runtime sources, gameplay state and active DLLs are unchanged. A native CMake build of the staged *copy* enables the existing `rd_execution_events.hpp` publisher and independent Tk viewer. Game display remains in `rd_runtime_host` and SMS video remains in `rd_video_sms_mode4`; the monitor merely subscribes to `controller.diagnostics` (CPU-neutral). `--video capture --input neutral --no-viewer` supports headless smoke tests; normal preview defaults to a game window, live buttons and instruction viewer. GUI/Tk availability on Windows is an owner acceptance gate.

The service records last observed input changes and the guest PC, physical ROM offset, frame and stop state. It generates a three-file, SHA-256-manifested, redacted diagnostics ZIP outside AppData: `preview.json`, `monitor-events.jsonl` and `manifest.json`. No ROM source, native binary or machine-local paths are placed inside the upload ZIP. A temporal link between input and stop is **not** causation; real Z-button behaviour, gameplay correctness and debugging parity remain blocked. Sampling is bounded to 200,000 native events and ZIP excerpts at 5,000. There are no breakpoints, interactive instruction stepping, or automatic recovery from preview stops.

## v0.4.9.20 source-attested preview recovery stop

After a real native `UNTRANSLATED_*` or `BANKED_CODE_NOT_TRANSLATED` termination with matching event PC, the read-only preview ZIP includes `recovery-seed.json` containing actual mapper, stack pointer, PC, physical offset, ROM identity and step count. A default capture still never changes a recovery job. The user must explicitly submit the ZIP to a new bounded `resume --preview-stop` cycle. The window labels blocked guest execution rather than native process crash; guest VDP frame and host video frame are separate measurements and the observed two-frame difference is **not** declared corrected. Older ZIPs without actual mapper state cannot be used for recovery.

## v0.4.9.21 native C++ monitor and terminal-frame accounting

The new current-controller preview launches the independently built **native Win32** `RecompDevMonitor.exe` by absolute path from its compiled binary directory. The previous Tkinter source remains only for historical provenance and is not launched by the current preview worker. A local token-authenticated subscription is read-only and protocol-versioned; no CPU/console DLLs or ROM are loaded into the monitor. The video window remains the independent `rd_runtime_host` implementation. Linux preview tests run headless with `--no-viewer`; actual Windows GUI/keypress acceptance is pending.

`preview.json/frame_accounting` now distinguishes `host_output_frames`, `guest_vdp_frames_at_native_exit` and `last_sampled_guest_frame` (different clocks, not independent gameplay parity). A new `candidate-capture.json` may contain ordered host-video frame fingerprints with explicit unknown input/audio/state qualifications; it is never a reference-emulator capture. Archive event samples remain bounded to the last 5,000, with local source traces retained separately. `RECOMPDEV_GAMEPLAY_PARITY_QUALIFIED=FALSE` is mandatory.

## v0.4.9.22 native search, capture watches and UI throughput

The installed current-controller preview subscriber remains `RecompDevMonitor.exe`, not the historical Python/Tk script. `viewer_win32.cpp` ingests authenticated localhost controller events in a background Winsock thread into an 8,192-event bounded queue; the Win32 UI consumes at most 768 JSON events every 100 milliseconds. A 2,000-event bounded projection and incremental edit updates replace the v0.4.9.21 full trace rewrite. Display queue or broker overflow can lose *visible samples* and explicitly reports losses; neither queue is the authoritative native event log, which remains in private preview evidence. Diagnostic ZIP still embeds the last 5,000 events only and must not claim to include a full trace.

Use search text and field selection to find logical PC (supports leading-zero hex and inclusive `0xSTART:0xEND`), physical ROM offset (when provider supplies it), opcode class, event type or arbitrary text. `Matches only`, `Follow latest`, `Previous` and `Next` are read-only. Follow may be unchecked to retain the scroll position while new events arrive. A match in a sampled on-screen trace is not proof that every instruction was captured.

To capture all hits for selected guest logical PCs independent of sampling: `RecompDev.exe preview --job JOB --cycle N --monitor-pc 0x0BDB --monitor-pc-range 0x0BD8:0x0BE4 --monitor-matched-only`. Options can repeat (max 16 PC values and 16 ranges). The C++ controller validates address syntax and bounds before launching the Python orchestration bridge, which transmits watch configuration only via private native guest environment and records ROM-free watch configuration and hit counts in preview evidence. The generic native producer checks `pc` prior to ordinary sampling and tags `watch_hit`; overall native trace remains bounded at 200,000 events. Observing an address does not pause/step execution and never reads guest memory.

The old Tkinter viewer remains in historical source only. Python is still transitional for Ghidra/Rizin and private preview compilation, not the current monitor UI. Windows GUI stress acceptance, actual input/button parity, video/audio/device-state parity and trustworthy independent reference emulator capture remain **BLOCKED**.
