# v0.4.9.34 — Standalone Native Export MVP (source promotion)

**Product direction:** Resume the authoritative [roadmap](../project/ROADMAP.md) P0 standalone export and independent executable milestones instead of continuing infrastructure-only releases. The binding [DEVELOPMENT-CONTRACT.md](../project/DEVELOPMENT-CONTRACT.md) and [PREBUILD-v0.4.9.7.md](../project/PREBUILD-v0.4.9.7.md) remain in force.

**Promotion scope:** `git-main-only-no-runtime`, `infrastructure-source` as required by the existing canonical installer protocol. This is a product-capability source release, NOT a qualified active-runtime promotion or certified game conversion. Actual Windows installer Build/CTest and independent execution evidence are mandatory before promotion. Hardware parity, second ISA production proof, real Shinobi standalone run, clean-Windows-machine testing and rollback-capable production runtime activation remain **BLOCKED**.

## Working delivered capability

- `RecompDev.exe export demo --out <empty-directory>` compiles an original rights-cleared native-loop fixture from existing source and proves end-to-end compiled-controller export, without relying on a user-supplied game. `RecompDev.exe export build --project <generated-project> --source-data <authorised binary> --out <empty-directory> --rights-confirmed` delegates through the generic controller into the exporter, whose initial independently versioned source adapter consumes existing generated C++ without changing `translated.cpp`.
- Rights-confirmed source/data is embedded into the native EXE by the adapter. A standalone launch requires no original-ROM file path, controller, Python or compiler on the target system. The output does **not** contain a separate original source binary; SHA-256 identifiers are recorded in an explicit versioned release receipt.
- The trusted export CMake recipe compiles the native guest instructions, hardware services and host into a single application. The module contract is adapter-selected, not based on controller-internal Z80/SMS assumptions. Subsequent console support requires a new source adapter, not a hardcoded controller branch.
- Export fails closed on no rights confirmation, inconsistent source identity, missing code ABI, source symlinks, existing outputs and compilation failures. `export verify` checks immutable outputs, and a built-in isolated launch records actual native execution versus requested coverage.
- Both the compiled controller version and the source-bound live-game evidence release are now derived from authoritative workspace release identity instead of stale v29/v30 strings. Existing historical evidence is immutable and never relabelled.

## Exact acceptance scope

**Locally demonstrated on Linux:** a source-attested, original-code-generated Z80 synthetic fixture compiled to a standalone binary; independently ran without the original `.sms` file and progressed to `FRAME_BUDGET_REACHED` after 3 frames; another original fixture stopped honestly at untranslated bank code; bundle tampering and provenance mismatches were rejected. The Linux build is not a Windows executable and does not qualify owner MSVC or clean-machine runs.

**Not delivered:** complete automated ROM-to-export from raw import; portable compilerless generation; a standalone Windows game already tested by the owner; a complete absence of binary data (authorised data is embedded); complete code coverage; independent video, audio, input or timing parity; Mega Drive and PS1 active native plugins. All remain BLOCKED roadmap milestones. A source-only install must never replace active runtime binaries or modify historical source/ROM Git repositories.

**Integrity:** `export verify --expected-manifest-sha256 SHA256` supports out-of-band manifest pinning, because an unpinned SHA receipt is only a consistency check. The demo fixture deliberately does not assert native output graphics/controls or general gameplay parity.

## Pre-promotion Windows acceptance correction

The first v0.4.9.34 candidate **failed** the owner's full Windows suite (98/100). No Git promotion or runtime activation occurred. Two test defects were identified and corrected without changing the exporter implementation: a historical CLI test expected `0.4.9.30` instead of reading the authoritative build identity, and the symlink-rejection test attempted to create a Windows symlink without the required OS privilege. The corrected security test checks a real symlink where supported and exercises the export admission guard with a simulated link when Windows reports `WinError 1314`. These adjustments are part of this same unreleased v0.4.9.34 candidate, not a new version or a runtime deployment. **Full Windows CTest must rerun before source promotion.**
