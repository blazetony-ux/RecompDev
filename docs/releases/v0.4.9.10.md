## 2026-11-07 — WindowsFix3: source-attested runtime-gap recovery (candidate)

The owner WindowsFix2 native application completed 120 frames using independently linked SMS state, Mode-4 graphics and runtime-host DLLs, matching the previous build's 709,841 steps / 7,159,090 guest cycles / frame hashes / hardware counters. An existing explicit `--runtime-gap-report` workflow consumes **`PILOT_RESULT` native-pilot reports**, not the larger `NATIVE_APP_RESULT` output. A genuine pilot run is therefore still needed to supply bounded source-qualified recovery evidence; the controller does not invent a missing report. Previously, the controller used only stopped PC/mapper, discarding the pilot's observed SP; the CPU abstract interpreter then had to invalidate bank identity at a CALL whose stack write might hit the mapper. This correction propagates a *present, verified-range* observed SP into the Z80 analysis, preserving unknown-SP conservative behaviour. The Z80 CPU plugin now treats decoded relative/conditional branch and flag-only operations as mapper-neutral (rather than dropping known state), and source-lifts conditional JR NZ/Z/NC/C and unconditional JR from attested bytes. The new cross-platform test proves CALL → PUSH/POP → conditional JR → RET recovery only when observed SP supports safe stack writes, and rejects out-of-range SP. No game-specific opcode tables or offsets have been added.

The developer's local structural discovery on the original 256 KiB Shinobi ROM, using a **test-only reconstruction of the observed stop** with PC `0xB2E1`, mapper `[0,0,1,2]`, and SP `0xDFFC`, now yields 2,464 candidates versus 620 for the initial non-seeded search. The recovered instructions are not yet MSVC compiled or 1,800-frame executed in this revision; the source-only test cannot substitute for the owner's genuine native pilot report. The historic Ghidra base/bank exports are available only on the owner's Windows machine.
